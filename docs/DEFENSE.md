# Подготовка к защите практической работы 1

Новицкий Д.А., группа 5351. Тема: консольный симулятор службы доставки на Java.

## 1. Что нужно уметь объяснить

Программа моделирует заказ от создания до завершения. Данные находятся только в памяти. Пользователь создаёт заказ с несколькими товарами, выбирает доставку, назначает свободного курьера и переводит заказ по допустимым статусам. Главная цель работы — показать инкапсуляцию, композицию объектов, полиморфизм и разделение ответственности.

Не заучивайте только названия классов: перед защитой самостоятельно пройдите сценарий ниже и найдите в коде каждую проверку.

## 2. Подготовка компьютера

Нужен JDK 17 или новее. JDK включает компилятор javac и средства запуска; одной среды JRE недостаточно. В терминале выполните `java -version` и `javac -version`. Если команда не найдена, настройте JDK в IntelliJ IDEA или добавьте каталог bin установленного JDK в PATH. Проект проверен компилятором 21.0.9 с параметром `--release 17`, то есть использует язык и API Java 17.

В IntelliJ IDEA: Open → папка delivery-simulator; File → Project Structure → Project SDK → JDK 17+; у папки src выберите Mark Directory as → Sources Root; откройте Main.java и запустите main. Для тестов отметьте test как Test Sources Root и запустите DeliveryTests.main. Сторонние библиотеки не нужны. Кодировка файлов и консоли UTF-8.

Из PowerShell: перейдите в папку проекта, выполните `chcp 65001`, затем `./run.ps1`. Тесты запускаются `./test.ps1`. Если скрипты запрещены политикой, не обязательно менять политику: прямые команды javac и java приведены в README. В Linux/macOS: `sh run.sh` и `sh test.sh`.

После закрытия программы заказы исчезают — это соответствует заданию. Перед демонстрацией начните новый запуск, чтобы номера заказов совпадали со сценарием.

## 3. Краткое выступление на 2–3 минуты

«В работе реализован консольный симулятор службы доставки на Java. Заказ содержит клиента, адрес, позиции, выбранный способ доставки, курьера и статус. Создание заказа и просмотр списка выполняются через меню. Доставка реализована интерфейсом DeliveryMethod и тремя классами: StandardDelivery, ExpressDelivery и PickupDelivery. Стандартная доставка стоит 300 рублей, экспресс — 800, самовывоз бесплатный. У каждого способа есть ориентировочный срок и признак необходимости курьера.

Бизнес-правила находятся в Order, а не в меню. Например, нельзя отправить заказ без способа доставки или назначенного курьера, если курьер требуется. Допустима только цепочка CREATED → DELIVERING → COMPLETED. Для самовывоза промежуточный статус означает готовность к выдаче. После завершения курьер освобождается.

Поля закрыты, изменение состояния выполняется через проверяющие методы. Для стоимости использован BigDecimal, чтобы избежать ошибок двоичной арифметики. Сервис OrderManager хранит заказы в памяти, ConsoleInput отвечает за ввод, OrderPrinter — за вывод, ConsoleUI — за сценарии меню. Написаны 36 автоматических проверок и воспроизводимый консольный пример. Работа разделена на содержательные Git-коммиты».

## 5. Как читать исходный код

Начните с Main: он создаёт Scanner, поток UTF-8, OrderManager и ConsoleUI. Метод main не содержит правил заказов. Далее смотрите ConsoleUI.start: цикл меню, switch, вызовы небольших методов и обработка исключений. В createOrder ввод сначала собирается в локальные переменные и список. OrderManager получает его только после завершения ввода: EOF не оставит частично заполненный заказ в хранилище.

OrderManager содержит LinkedHashMap<Integer, Order>. Ключ — уникальный номер, значение — заказ. LinkedHashMap сохраняет порядок создания при выводе. В среднем поиск по номеру O(1). nextId увеличивается только после успешного создания. Список курьеров заранее содержит Ивана и Анну. Добавление курьеров через меню не требовалось заданием.

Order — основной объект с изменяемым состоянием. requireCreated запрещает правки после начала исполнения. addItem проверяет статус и null. setDeliveryMethod освобождает курьера при самовывозе. assignCourier проверяет статус, наличие способа и необходимость курьера. candidate.reserve вызывается до освобождения старого курьера: при отказе замены прежнее назначение сохраняется. changeStatus проверяет допустимый переход, готовность заказа и освобождает курьера при завершении.

Client и OrderItem неизменяемы: final-поля, нет сеттеров. Courier хранит activeOrderId, а не публично изменяемый boolean. Методы reserve и release имеют пакетный доступ: это внутренние операции модели, а внешний интерфейс использует Order.assignCourier. getCourier у завершённого заказа сохраняет ссылку как историю исполнителя; isAvailable у самого курьера уже true.

DeliveryMethod задаёт getName, calculateCost, getEstimatedTime, requiresCourier. Order вызывает их через интерфейс, не проверяя конкретный класс. ConsoleUI хранит список стратегий и выбирает элемент по номеру. OrderStatus перечисляет три допустимых состояния и знает граф переходов. Validation содержит повторяющиеся проверки строк и цен.

ConsoleInput читает только nextLine, затем разбирает число. Нет смешивания nextInt и nextLine и проблемы оставшегося перевода строки. integer ловит NumberFormatException, включая переполнение int, и повторяет запрос. price разрешает десятичную точку или запятую, но не NaN, Infinity, отрицательные значения или более двух дробных цифр. OrderPrinter только выводит сведения и не меняет объекты.

## 6. Принципы ООП на конкретных примерах

**Инкапсуляция.** Это не просто private. Нельзя присвоить order.status напрямую или вызвать произвольный setStatus: есть changeStatus с проверками. Список позиций возвращается через List.copyOf, поэтому getItems().clear() не разрушит состояние. Сама копия списка не делает элементы неизменяемыми, поэтому OrderItem также неизменяем.

**Абстракция.** DeliveryMethod описывает то, что требуется от доставки, без деталей конкретного тарифа. Пользователь Order видит контракт, а не устройство класса.

**Полиморфизм.** В переменной DeliveryMethod может находиться объект любого из трёх классов. Вызов calculateCost выбирает реализацию фактического объекта во время исполнения. Это переопределение методов, не перегрузка.

**Композиция объектов.** Заказ построен из ссылок на клиента, позиции и доставку. Формулировку задания о композиции следует отличать от строгого UML-владения жизненным циклом: клиент и стратегия переданы извне и могут использоваться другими объектами. Позиции — логическая составная часть заказа, но Java не запрещает передать один неизменяемый OrderItem двум заказам. Не утверждайте, что сборщик мусора удаляет позиции сразу при удалении заказа.

**Наследование.** Здесь используется реализация общего интерфейса implements, а не иерархия extends для всех сущностей. Не нужно наследовать Courier от Client: роли имеют разное поведение и искусственный общий родитель только усложнил бы модель.

**Разделение ответственности.** Main собирает компоненты, UI координирует действия, Input разбирает ввод, Printer форматирует сведения, Manager хранит и находит объекты, Order защищает правила. Это позволяет проверять модель без настоящего терминала.

**Стратегия.** Три класса доставки — пример паттерна Strategy: алгоритм стоимости и правила курьера заменяются объектом общего интерфейса. Чтобы добавить новый способ, реализуйте интерфейс и добавьте объект в список methods. Order менять не нужно, если новый способ укладывается в существующий контракт.

## 7. Деньги и статусы

Формула: сумма товаров = Σ(цена × количество); итог = сумма товаров + тариф. BigDecimal создаётся из строки, например new BigDecimal("199.90"), а не из double. У double значение 0.1 нельзя точно представить в двоичной системе. Денежный масштаб нормализуется до 2 через setScale с UNNECESSARY: лишняя ненулевая точность не округляется молча, а отклоняется.

CREATED — можно редактировать позиции, способ и курьера. DELIVERING — заказ в пути или готов к выдаче. COMPLETED — терминальное состояние. Нельзя CREATED → COMPLETED, нельзя назад и нельзя повторить текущий статус. Для самовывоза сохранён единый граф без лишнего отдельного состояния READY_FOR_PICKUP; смысл промежуточного статуса указан в интерфейсе. Это осознанное упрощение модели.

## 8. Вопросы и короткие ответы

**Почему интерфейс, а не абстрактный класс?** Общего изменяемого состояния нет, нужен контракт поведения. Интерфейс проще и не занимает единственное наследование класса.

**Где проверяются бизнес-правила?** В Order и Courier; UI только показывает ошибки. Даже прямой вызов модели не позволит пропустить статус.

**Почему final у классов и полей?** final-поле нельзя переназначить после конструктора, final-класс нельзя наследовать. Но final List не запрещает менять содержимое: для защиты нужен закрытый список и неизменяемая копия.

**Почему нет instanceof?** Метод requiresCourier выражает нужное свойство способа доставки через контракт. При добавлении нового бескурьерского способа правила сохранятся без изменения Order.

**Чем перегрузка отличается от переопределения?** Перегрузка — одно имя, разные параметры; выбор сигнатуры при компиляции. Переопределение — реализация метода контракта подклассом или классом интерфейса; выбор реализации по объекту.

**Почему исключения?** Невалидные аргументы дают IllegalArgumentException, недопустимое действие в текущем состоянии — IllegalStateException. Консоль перехватывает их и выводит сообщение. Ошибка не должна превращаться в успешную операцию.

**Что при EOF?** Программа выводит сообщение и выходит; частичный новый заказ не сохраняется. Явная команда выхода — пункт 6.

**Есть ли база данных?** Нет, условие допускает работу только в памяти. GitHub хранит исходники, а не текущие заказы.

**Почему телефон не проверяется регулярным выражением?** В задании формат не задан. Требуется непустая строка; реальная телефонная валидация — отдельная задача и не подтверждает существование номера.

**Можно ли одновременно доставлять два заказа одним курьером?** Нет, учебная модель допускает одно активное назначение. После завершения либо перехода к самовывозу он свободен.

**Почему заказ хранит ссылку на курьера после завершения?** Это история исполнителя. Занятость хранится в Courier и уже освобождена.

**Потокобезопасна ли программа?** Нет, она однопоточная. Проверка и резервирование не являются межпоточной транзакцией. Для многопоточного сервера понадобилась бы синхронизация либо транзакционное хранилище.

**Почему не JUnit?** Для этой работы достаточно автономного тестового main без внешних зависимостей. check бросает AssertionError, процесс завершается с ошибкой. Это не Java assert: параметр -ea не требуется.

**Какие ограничения?** Нет сохранения, отмены и удаления заказа, расчёта маршрута, редактирования клиента и добавления курьеров через меню. Это не обязательные функции исходного задания. Тарифы и сроки учебные и фиксированные.

## 9. Что проверяют тесты

36 проверок проверяют контракт, а не только счастливый сценарий: пустые поля, количество, отрицательную и слишком точную цену; точность расчёта; номера заказов; отсутствие неизвестного заказа; защиту списков; запрет пропуска статуса; необходимость способа и курьера; все три тарифа; занятость курьера; неудачную и успешную замену; освобождение при самовывозе и завершении; запрет изменения отправленного заказа; повторный и обратный статус; пустой заказ; неверный ввод и EOF.

Фактический основной пример: 549,80 руб. товары + 800 руб. экспресс = 1349,80 руб. Вначале попытка отправки без курьера отклоняется, после назначения заказ проходит все состояния.

## 10. Git и обоснование коммитов

Репозиторий: https://github.com/deniskan2007-sketch/Delivery. Каждый коммит добавляет отдельную часть: каркас; клиента и позицию; курьера; стратегии доставки; правила заказа; сервис; ввод и вывод; меню; скрипты сборки; тесты; исправление UTF-8 с примером; описание архитектуры; материал для защиты; оформленный отчёт. Всего планируется 14 содержательных этапов. Это реальные изменения файлов, а не пустые коммиты для количества.

Команды для объяснения: `git status` — незакоммиченные изменения; `git log --oneline` — история; `git show <hash>` — конкретный этап; `git diff` — ещё не сохранённые различия; `git add` — подготовка изменений; `git commit` — локальный снимок; `git push` — передача в удалённый репозиторий. Коммит не равен push: один push может передать много коммитов.
